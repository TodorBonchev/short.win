## Why reusing the buffer is the right first move

The local Agave 4.1.2 CLI help explicitly calls `--buffer` an intermediate account that can resume a failed deploy. The matching [Agave v4.1.2 deploy source](https://github.com/anza-xyz/agave/blob/v4.1.2/cli/src/program.rs#L1262-L1454) accepts an existing buffer pubkey (the existing account needs no buffer keypair for the upload), checks loader ownership, authority and length, and fetches its bytes. Its [write loop](https://github.com/anza-xyz/agave/blob/v4.1.2/cli/src/program.rs#L2535-L2663) queues only chunks that differ from the ELF; when an existing buffer is supplied it does not recreate or refund/recharge the buffer's rent. The observed 14 exact 960-byte chunks and 8.352520760 SOL in the buffer are therefore useful progress; the spinner count should not be treated as a complete measurement of on-chain bytes without re-reading the buffer. The 16.647399240 SOL payer balance still covers the estimated final allocation plus fees while retaining the selected reserve, subject to the immediate preflight balance/rent check.

Closing the buffer now would abandon those verified bytes and require allocating and uploading again. Solana documents that an interrupted deployment may leave a recoverable buffer, and `solana program close <buffer>` can recover its lamports if the attempt is intentionally abandoned; a completed loader-v3 deployment consumes the buffer and moves its funding into ProgramData. [Solana production readiness](https://solana.com/docs/tools/production-readiness#deployment-process); [loader-v3 deployment](https://solana.com/docs/core/programs/program-deployment); [Solana CLI reference](https://solana.com/docs/references/solana-cli).

## Retry flag and routing evidence

The initial CLI invocation used `--max-sign-attempts 1`. In [Agave's sender](https://github.com/anza-xyz/agave/blob/v4.1.2/client/src/send_and_confirm_transactions_in_parallel.rs#L435-L560), that value is the number of blockhash signing cycles. Its exact `Max retries exceeded` error is returned when writes remain unconfirmed after those cycles. Raising it to 5 directly addresses transient expiry or landing delays; it does **not** cure an RPC or transport capacity problem, and more cycles may incur additional transaction fees. The error does not by itself prove rate limiting. The first missing write simulated successfully, which supports the transaction's validity but says nothing about bulk delivery.

The original `--use-rpc` forces writes through `sendTransaction` on `api.devnet.solana.com` ([Agave CLI sender](https://github.com/anza-xyz/agave/blob/v4.1.2/cli/src/program.rs#L3160-L3216)). The sender schedules messages 10 ms apart, approximately 100 writes/s ([Agave transaction sender](https://github.com/anza-xyz/agave/blob/v4.1.2/client/src/send_and_confirm_transactions_in_parallel.rs#L263-L329)), while Solana publishes a changeable public devnet limit of 100 requests/10 s/IP and 40 requests/10 s/IP for a single RPC method. Its public endpoint has no guaranteed write capacity for this burst. [Solana cluster limits](https://solana.com/docs/references/clusters#devnet-rate-limits). The mismatch makes public-RPC throttling a strong hypothesis, **not a proven diagnosis**: there was no captured HTTP 429/403 response or RPC operator incident record in the evidence examined.

Without `--use-rpc`, the same Agave sender creates a QUIC TPU client and attempts to send directly; if that send fails or times out after 5 seconds it falls back to RPC. It still queries RPC for blockhashes and batched signature statuses. QUIC access from this host and public RPC read capacity for ~1,699 remaining writes have not been proven. [Agave CLI route selection](https://github.com/anza-xyz/agave/blob/v4.1.2/cli/src/program.rs#L3160-L3216); [Agave fallback and confirmation](https://github.com/anza-xyz/agave/blob/v4.1.2/client/src/send_and_confirm_transactions_in_parallel.rs#L108-L165); [Agave send fallback](https://github.com/anza-xyz/agave/blob/v4.1.2/client/src/send_and_confirm_transactions_in_parallel.rs#L193-L260).

There is no verified free devnet RPC service in this research with enough documented burst write quota for this CLI path. As an example of why plan labels alone are insufficient, Helius currently advertises 1, 5, 50 and 100 `sendTransaction`/s on Free, Developer, Business and Professional respectively; only its $999/month Professional shared tier reaches the CLI's nominal 100/s, leaving little burst margin, and no endpoint/account was tested here. A paid purchase solely for this devnet rehearsal is not the first recommendation. [Helius rate limits and pricing](https://www.helius.dev/pricing). Confirm any chosen provider's devnet support, current method-specific limits, routing and WSS URL before using it. [Solana provider selection guide](https://solana.com/docs/rpc/providers).
