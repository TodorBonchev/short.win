# AI3-FR01: quarantine legacy empty-pool carry

Date: 2026-10-19. Base: `7c5ae42978a32cd7463c6cef991031485c39abb2`.
This is a further **unreleased 1.0.3** fix, superseding the earlier candidate's deposit
behavior and program hashes. The finding remains **in progress** under AUDIT §12;
this record is not a release, 24-hour fuzz result, or owner acceptance of historical loss.

## Correction and availability boundary

At the start of `pool::deposit_in`, before release, touch, share minting or wipe-record
finalization, refuse a deposit when `total_shares == 0` and either `carry != 0` or
`carry_r != 0`. Math error **14 `LegacyPoolCarry`** maps to the appended program error
**6110 `LegacyPoolCarry`**. Existing codes are unchanged. The Python reference model,
IDL/generated client and WASM/browser preview agree; the browser marks this condition
blocked and explains that sweeps and retries cannot resolve it.

This closes the next-cohort capture path by quarantining the affected pool. It deliberately
preserves both carries, lender SOL, pot backing, old allocated claims and epoch records.
It neither erases value nor guesses a recipient: the old state has no authenticated record
of the departed final owner's identity. Claims by existing lenders still work. No affected
deployed market is asserted or inspected by this change.

**Availability cost:** an affected already-empty pool cannot accept any new deposit until
a separately reviewed recovery/migration handles it. Ordinary sweeps cannot clear the
pool carries. The guard applies even to sub-lamport remainders and an unexpected signed
negative entitlement carry; it does not try to classify historical balances by size.
Nonempty pools retain their existing carry behavior. A clean empty pool remains usable
even with old allocated claims, unmatched pot or rounding dust. Carries in an old full-wipe
`ShareEpoch` record are separate and do not quarantine a pool whose current carries are zero.
No new account layout, instruction, authority or transfer is introduced; the new error is
an append to the existing error interface. Package version remains the unreleased 1.0.3.

Historical ownership/recovery and the other unresolved pot/fee/incentive findings remain
open. This quarantine does not claim to pay the departed lender or complete a migration.
The [known-issues register](../known-issues.md#8-open-items-from-the-103-fix-review) records
that narrower behavior and its availability bound.

## Regression and negative controls

- **Persisted predecessor state:** `tests/fixtures/legacy_empty_carry.canonical` is the
  complete canonical state generated by the unmodified `b815269` public math API in the
  [independent accounting review](independent-accounting-1.0.3.md). The new test
  reconstructs the old withdrawal and compares the entire state to that checked-in witness.
  With both source bits completed, attempts to deposit a one-token new cohort return the
  migration-required error and leave every math input unchanged, including repeated retries
  and both `rewards_required` settings. The historical 1,000 lamports are preserved.
- **Boundary matrix:** each carry alone, whole-lamport and one-unit fractional residues,
  signed negative carry, pending/completed sweeps and both reward modes are refused.
  Existing tests retain nonempty carry behavior and old zero-share claims; the dust test
  now also proves that a clean empty pool's new cohort receives only its own income.
- **Old-source control:** the new regressions with the exact `7c5ae429` pool source fail
  (two expected failures). In particular, the completed-sweep legacy deposit returns
  `Ok(1000)` shares instead of refusal. Only the new error definition/test harness was
  retained so the same assertions compile; this is an isolated source control.
- **Signed program transactions:** the new `lender_it` adversarial regression seeds an
  explicitly labelled legacy snapshot, completes a real source sweep, and submits signed
  deposits with paired and asymmetric carries. The new ELF returns 6110 with all affected
  accounts unchanged, including rollback of the newly initialized lender PDA/rent. An
  old shareless claimant can still receive its seven allocated lamports, and the zero-carry
  control admits the deposit. Against the prior verified `b88aa520…` release, the same
  test fails because the deposit actually succeeds. This fixture is not a live upgrade
  transaction or proof of a deployed affected market.
- **Model and browser:** the model exercises 48 refused attempts and four compatibility
  controls, including full-wipe record carry and preserved old pot claims. Removing only
  its guard reproduces the 1,001-lamport next-cohort payout. Actual rebuilt-WASM browser
  previews refuse both carry fields with or without bundled sweeps and retain clean controls.
